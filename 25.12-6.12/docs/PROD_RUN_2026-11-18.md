## 3. 本轮修好的问题

### 3.1 WAN eth1 无收包（0037）

`nsscc` 的 `nss_cc_parent_data_0` 索引 4..9 指向 UNIPHY0/1/2 的 NSS RX/TX 时钟，
这些时钟由主线 PCS 驱动注册。板级 DTS 把 `pcs0/1/2` 全 disabled 且内核未开
`CONFIG_PCS_QCOM_IPQ9574`，父时钟解析全 NULL，`__clk_rcg2_select_conf` 每次
determine_rate 都 WARN，port5（WAN）时钟设不上 → RX 恒 0。

修复：`CONFIG_PCS_QCOM_IPQ9574=y` + `&pcs0/1/2 { status = "okay"; }`（补丁 0037）。
CCF 父时钟懒解析且不缓存失败，与 nsscc 的 probe 顺序无关；qca-ssdk 用裸 ioremap
访问同一 UNIPHY 块，与 PCS 驱动的 `devm_platform_ioremap_resource` 不冲突。

### 3.2 MDIO 扫描丢 0x10–0x13/0x1c（0150，真机 v3 已验证）

上游 6.12 mdio-ipq4019 不脉冲整条 `phy-reset-gpio` 数组。补丁 0150 在 probe 时
`devm_gpiod_get_array_optional(..., "phy-reset", GPIOD_OUT_LOW)`，扫描前整数组
100 ms 拉低 + 1 s 静置；DTS 去掉总线级/per-PHY reset-gpios，把 `phy-reset-gpio`
留给 qca-ssdk。真机 `ls /sys/bus/mdio_bus/devices/` 六个设备齐全。

## 10. 下午插曲：0037 v2（删 pcs resets）导致全部端口无流量

### 10.1 动机与改动

上午镜像里每启动 3 条 `__reset_control_get_internal` WARN（`ssdk_gcc_clock_init`
阶段，qca-ssdk 以独占方式取 uniphy0/1/2_xpcs_rst，PCS 驱动再取就报共享/独占
冲突）。0037 v2 在 `&pcs0/1/2` 覆盖里加 `/delete-property/ resets;`，想让
qca-ssdk 成为唯一持有者、消掉这 3 条噪声。

### 10.2 现象

刷入后设备完全不可达：10G 口、1G 口都零帧，主机侧只看到自己的 ARP/DHCP/RS
帧。断电重启无效。

### 10.3 取证（从 TFTP RAM 系统只读挂 p27 尾部 overlay）

- overlay 里 `upper/sbe-boot-trace/events.log` 有完整两次启动记录，均以
  `nss-load: boot #N: tier wired loaded` 结束；
- `/etc/config/network` 已由 uci-defaults 生成（br-lan 192.168.1.1/24、eth1 dhcp），
  并有 overlayfs 删除白洞（char 设备 0/0）；
- overlay ext4 起始偏移等于本次 root 成员长度（78,643,200 B），确认属于这次安装。

结论：镜像**进得了用户态**，故障是端口初始化，不是启动失败。

### 10.4 根因

ssdk 用 `ssdk_gcc_reset_ids_init()` 独占请求 uniphy0/1/2_xpcs_rst。本内核未定义
`SSDK_RAW_CLOCK`，`ssdk_gcc_reset()` 落到真实的 `reset_control_assert/deassert`。
DTS 里保留 resets 时 ssdk 的句柄是 `-EBUSY`、调用早返回；删掉属性后
`ssdk_uniphy_reset()`（`ssdk_clk.c:2710`、`adpt_hppe_uniphy.c:272…`）在初始化时
真去翻转三条 UNIPHY XPCS 复位 → 所有 dp netdev 注册失败 → 全端口无流量。

### 10.5 处理

- 回退 0037 到 v3：`pcs0/1/2` 仍 `status = "okay"`，`resets` 保留，接受 3 条
  WARN 为已知噪声（PCS 驱动只消费时钟，本内核无带 pcs-handle 的 dp 端口，
  从不 assert 该句柄）；
- 构建树与补丁同步（`grep -c "delete-property/ resets"` = 0），增量重编；
- 按用户要求先刷回 24.10 v95-1 让设备可用（同一镜像 `sysupgrade -F -n` 静默
  无效的坑见 §4，最终仍用 `reflash-v951.sh` 手工 dd，p25/p27 读回全 match、
  `REFLASH_OK`），确认 br-lan 192.168.1.1、WAN DHCP、三 SSID、LuCI 200；
- 重编完成后再从 24.10 `sysupgrade -F -n` 刷入 25.12 v3。

## 11. radioN 编号与频段错位（0038）

### 11.1 现象

首启镜像（§10.6）上 `radio0`=6G、`radio1`=5G、`radio2`=2.4G，与 24.10 的
radio0/1/2 = 2.4G/5G/6G 相反；频段、SSID、信道本身都正确。

### 11.2 根因

25.12 的无线默认配置由 `wifi-scripts` 的 ucode 生成器（
`package/network/config/wifi-scripts/files/lib/wifi/mac80211.uc`）负责，而
`/etc/hotplug.d/ieee80211/10-wifi-detect` 在**每块 phy 热插拔时**都会跑一次
`/sbin/wifi config`。生成器对新射频用 `while (config[radio$idx]) idx++`
取最小空闲编号，于是 `radioN` 取决于 ath12k 三块 PCIe 卡的探测先后；本板
不同启动的注册顺序并不固定（12:49 那次 0001/0003/0002，13:04 那次
phy0=6G/phy2=2.4G），首启时谁先到谁就是 radio0。24.10 的 shell 版生成器
顺序固定，因此没有这个问题。

### 11.3 修复（补丁 0038）

`25.12-6.12/patches/0038-wifi-scripts-name-radios-by-band.patch`：把默认编号
钉在频段上（2G→radio0、5G→radio1、6G→radio2），目标编号被占用（一个 phy 带
多个 radio、多个同频 phy）时回退最小空闲编号。设备侧先做离线验证（清空配置
只跑生成器读输出）：正常 board.json 顺序与整体反转顺序都得到
radio0=2g、radio1=5g、radio2=6g。

## 12. 无线概览页射频顺序（0039）

### 12.1 现象

0038 落地后 radioN 与频段对应正确，但用户指出「网络 → 无线」概览页的
射频块顺序是 radio2、radio1、radio0，期望 radio0、radio1、radio2。
真机取证：`/etc/config/wireless` 的段落顺序与页面显示完全一致
（radio2 在第 2 行、radio1 第 36 行、radio0 第 71 行），`ubus call
network.wireless status` 的键顺序也相同。

### 12.2 根因

`luci-mod-network` 的 `view/network/wireless.js` 在 `s.load` 里想按名字
排序射频，比较器却写成 `return a.getName() > b.getName();` —— 返回布尔值
而非负数/零/正数。`Array#sort` 拿到这种比较器构不成合法比较关系，实测
（Node/V8）对正序、逆序输入都原样返回，等于不排序；页面于是沿用
`network.getWifiDevices()` 的顺序，也就是 UCI 段落顺序。

段落顺序本身又跟随 ath12k 探测顺序：`/etc/hotplug.d/ieee80211/10-wifi-detect`
每块 phy 上电触发一次 `/sbin/wifi config`，先到先写（0038 只钉名字，不改
写入先后）。所以同一固件不同刷机的段落顺序会变，显示顺序随之变。

`luci-mod-status` 的 `view/status/include/60_wifi.js`（状态→概览的无线块）
是同一问题的变体：`radios.sort((a, b) => { a.getName() > b.getName() })`
的箭头函数体是块语句、没有 return，比较器恒为 undefined，同样不排序。

### 12.3 修法

`25.12-6.12/patches/0039-luci-sort-radios-by-name.patch`：把两处比较器
改为上游 master 已有的 `a.getName().localeCompare(b.getName())`。排序键是
段落名，radioN 在 N<10 时字典序与十进制顺序一致。补丁 `--fuzz=0` 干跑
干净应用；只重编 `luci-mod-network` 与 `luci-mod-status` 两个包。
