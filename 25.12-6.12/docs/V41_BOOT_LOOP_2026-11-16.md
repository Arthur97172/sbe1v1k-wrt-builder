# 25.12-6.12 run 41（b0a7389，NSS 分层）在路由器 B 上启动失败：真机观察记录

日期：2026-11-16
设备：SBE1V1K（B 机）
镜像：`build-25.12-6.12.yml` run 41 的产物，构建提交 `b0a7389`
（含 `0030-qualcommbe-disable-upstream-qca808x-phy` 与 NSS 分层装载默认档
`wired`，见 [NSS_AUTOLOAD_OFF.md](NSS_AUTOLOAD_OFF.md)）。
该次运行的 Release 作业因 token 403 失败，GitHub 上没有对应 Release 资产；
镜像由用户手动下载并在刷入前自行核对。

## 结论

**FAIL。** 刷入后设备进入约 3–4 分钟一轮的重启循环，局域网侧每轮只观察到
PHY 载波、**零帧**，`192.168.1.1` 全程不可达，无法登录取证。指纹与此前
v34 的"上电后只有 PHY 载波、零帧"一致（见
[V21_BOOT_AND_FAN_FIX.md](V21_BOOT_AND_FAN_FIX.md) 与项目记忆
`v34-hang-after-s10boot`）：崩溃发生在用户态网络初始化之前，NSS 分层机制
所在的 `/sbe-boot-trace/events.log` 等证据根本到不了。
随后经恢复模式刷回 24.10 v94，设备完全恢复（见下）。

## 刷入与观察方式

- 刷入方式：用户在 24.10 v94 系统上手动刷入（keep-config 与否未记录；
  按 25.12 首启语义建议下次用 `-n`，本条记为未知）。
- 观察手段（主机 USB 网卡直连 B 的 LAN 口，全程只读）：
  - 每 5 秒 ping + SSH 身份探测 + HTTP 状态码；
  - 每秒采样 `/sys/class/net/<iface>/carrier` 与协商速率，记录链路变化；
  - 载波每次变化时采样 NIC 的 `rx_packets` 增量。
- 没有串口线，崩溃现场（内核日志、pstore/ramoops、panic 输出）无法获取。

## 现场事实（按时间顺序）

1. 刷写命令提交后，旧系统关闭（SSH 端口先拒绝，随后链路断）；
2. 新系统开始以约 3–4 分钟为周期反复重启（用户观察，期间 WiFi SSID 反复出现消失）；
3. 网线在 eth2（1G LAN 口）上实测：PHY 每轮 `carrier=1 speed=1000` 持续
   **69–70 秒**，然后 `carrier=0` 约 14 秒，周而复始；
4. **PHY 亮着的整个窗口内，主机侧 `rx_packets` 增量恒为 0**——没有 DHCP、
   没有 IPv6 邻居发现、没有 ARP，ping 全部超时；
5. 网线在 eth0（10G，RTL8261N）上时 `carrier` 恒为 1（该 PHY 在整机复位后
   仍维持链路，不能作为"系统在跑"的指标，与此前 24.10 的观察一致）；
6. 观察窗口内一次都没有出现可 SSH 的瞬间，因此 `nss-load status`、
   `/etc/nss.conf`、`/sbe-boot-trace/events.log`、dmesg/logread 均未取得。

## 判读

- "PHY 亮 70 秒 + 零帧 + 周期性复位"更像**内核卡死后被看门狗/复位逻辑
  整机重启**，而不是 panic 后主动重启（后者通常会留下 pstore 或更短的复位
  周期）。与 v34 后 S10 阶段的 QSDK 等待循环（无超时）假设一致。
- 0024（装载地址）、0027（CPU OPP/sleep_clk/NSS 保留区）、0030（qca8084-phy
  重名）与 NSS 分层默认档都未能改变这类启动失败；崩溃点应在这些修复生效之前。
- 以上为外推：无串口、无内核日志，卡点的具体位置仍属 **UNVERIFIED**。

## 回滚（已验证）

Reset+TFTP 进官方 RAM 系统（SNAPSHOT `r38189-706052b20f` / 6.18.60），
管道上传 24.10 v94 镜像（`20bfa3e07ebfe7df0aa228992beefa2cfc7d16b7d1c66206cf4a3595310e7290`，
82,576,166 B），设备内 sha256 逐字节一致后 `sysupgrade -F -n`。
约 2.5 分钟恢复，验证：`24.10-SNAPSHOT sbe1v1k-g3.5c` / 6.6.147 /
`root=/dev/mmcblk0p27` / overlay 已挂 / LuCI HTTP 200 / 三频 WiFi 广播 /
WAN 192.168.10.123 / 设备 ping 8.8.8.8 零丢包。

## 后续（离线归因方向）

1. 以 24.10-6.6 已跑通的 6.6 树为基准，逐项比对 25.12 6.12 树在 S10 之前
   的 QSDK 初始化路径（等待循环、时钟/PLL、NSS 保留区访问）；
2. 检查 6.12 内核下 `qcom_wdt`/复位源在无串口情况下能否通过 pstore/ramoops

3. 在拿到新的针对性补丁之前，不再向 B 机刷同类 25.12 镜像。

## 归因定案（2026-11-17，diag v20–v22 真机）

本文「后续」里的离线归因方向已被 diag 系列实验完成，不再需要从 S10 之前
的 QSDK 初始化路径查起：

- v20/v21 分层装载把复位钉死在 `modprobe qca-nss-ppe`：6.11+ 的
  `register_sysctl()` 宏把 QSDK ctl_table 数组的 `{}` 哨兵计入条目数，
  `sysctl_check_table()` 校验失败 → 注册返回 NULL → `ppe_drv_module_init`
  错误拆除路径在 `ppe_drv_get_qdisc_rule_flag` 处 PAN oops → panic=20 复位；
- 修复补丁 `nss/patches/qca-nss-ppe/0025-sysctl-register-sz-6.12.patch`、
  `nss/patches/qca-nss-dp/0008-edma-sysctl-register-sz-6.12.patch`；
- v22（diag + tier=wired + 修复）PASS：sdk/ppe/dp 一次装载、0 次 oops、
  eth0..eth3 + br-lan + 有线管理面 + 三频 WiFi 全部正常。

「PHY 亮 70 秒 + 零帧 + 周期复位」的看门狗/复位源假设就此作废：死因是
S15 装载 NSS 时的确定性 panic，与 0024/0027/0030 无关（它们生效之前就崩）。
完整证据见 `docs/DIAG_RUN_2026-11-16.md` §27–§29。生产镜像重建与真机
验证随后进行（结论另行记录）。
